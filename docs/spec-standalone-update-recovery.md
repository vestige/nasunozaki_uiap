# 保存開始時の残留更新状態と復帰（#69）

## 現状と段階

#65は「今回送った命令の応答が失われた場合」を扱う。#69は「保存を始める前から更新中の状態がある場合」を扱う。2026-10-18の実機では、本番のBEGIN status2がUSB通常再接続等で解消した。残留状態が有力だが、他の接続タブも切り離したため原因の断定はしない。

第一段階はブラウザ側の同時保存防止と安全な案内。ファーム・配布物は変更しない。この段階だけでは状態照会や、USBを抜かない復帰は完成しない。

## 第一段階：既存ファームでの安全性

- 保存を始める前にWeb Locksの排他ロックを取得する。空いていなければ通信前に拒否し、待ち行列には積まない。待ち行列で古い作品が後から保存されるのを避ける。
- シリアル番号を利用できないため、同一originの全UIAPduino保存を1つの名前で保守的に直列化する。複数ボードでも同時保存できない制約を許容する。
- ロックは通信・GET_REPORT回復・後処理がすべて終了するまで保持する。成功、失敗、ロック要求の例外でも解放する。ページ終了時はブラウザの管理するロックが解放されるが、ボードの状態は残り得る。
- Web Locks非対応時は同じページ内だけ二重保存を防ぐ。旧ページ、別origin（localhostとGitHub Pagesを含む）、別ブラウザ、直接通信するツールは排他できない。このロックはボードの所有権ではない。
- 「ためす」等の保存以外の通信はこのロックの対象外。保存中に別画面からボードを操作しないことが必要であり、全通信の排他は後続設計で扱う。
- BEGINの明示的な拒否は型付きエラーにする。status2の場合は残留状態の可能性と通常USB再接続手順を表示する。他のstatusを同じ理由と扱わない。
- status2は不正形式／長さ／更新中を区別できないため、原因を断定せず、ABORTやBEGIN再送は行わない。
- 別画面のかきこみが完了するまで待つ案内を先に出す。通常再接続で以前の作品が動く可能性を明記する。案内を開閉する操作だけではボードへ送信しない。
- 既存の上書き確認でキャンセルした場合は、保存関数へ進まず、ボードの状態も変更しない。

## 第二段階：USBを抜かない復帰のための設計条件

「更新中」という1bitだけを追加しても、別クライアントが保存中なのか残留なのかは判別できない。明示確認だけで無条件ABORTする方式も、別画面の作品を破棄し得るため採用しない。

次の条件を満たす所有権付き更新プロトコルを設計する。

1. 読み取り専用の機能照会・更新状態照会を追加し、既存のSTATUS（有効bank）と応答封筒を壊さない。
2. BEGINで所有トークン／更新世代を確立し、DATA・COMMIT・ABORTの各操作で一致を確認する。復帰後に旧送信元が再開しても、新しい作品へ古いDATAを書けないことが必要。
3. 他人の更新を取り消せる条件を、最終進行時刻と期限・世代等でボード側にも保持する。照会と解除の間に進行した場合は解除を拒否する。単なるブラウザ側の待機時間で所有者不在を判断しない。
4. 正常な進行・長時間のブラウザ停止・切断・再接続・時計周回・ボード再起動での期限規則を決める。期限切れの転送は再開ではなく、新しい所有権でやり直す。
5. 利用者が確認したときだけ、条件付き解除を要求する。キャンセルは読み取りのみ。解除成功の確認前に新しいBEGINを自動送信しない。
6. COMMIT完了後にACKを失った場合は、有効bankと世代／作品識別で保存済みを判定し、復帰対象と混同しない。
7. 既存ファームおよび旧クライアントとの互換性を定義する。所有権を確認できない相手へ新しい復帰操作を送らず、通常USB再接続を案内する。新方式の保存中は旧方式の破壊的命令を拒否する必要がある。
8. 全通信の排他範囲を決め、読み取り照会が別操作のACKキャッシュを上書きする影響も扱う。長い応答へ拡張する場合はUSB記述子・WebHID互換性を別途検証する。

この設計はファームの追加容量が必要。まずFlash／RAMを試算し、配布bin・ソース・build-infoを同時更新して公開用検証に通す。診断専用パッチ0x26を正式な更新状態APIの代用にしない。

## 第二段階の試作プロトコル（実機未確認）

共通封筒とInput Report 8 bytesは変更せず、次の命令を追加する。作品の形式versionとは別の転送方式であり、従来の形式1〜6をそのまま運ぶ。

| 命令 | 値 | payload |
| --- | --- | --- |
| OWNED_BEGIN | 0x40 | 所有識別子8 bytes + 従来のBEGIN payload5 bytes |
| OWNED_DATA | 0x41 | 所有識別子8 bytes + offset2 bytes + データ1〜14 bytes |
| OWNED_COMMIT | 0x42 | 所有識別子8 bytes |
| OWNED_ABORT | 0x43 | 所有識別子8 bytes |
| OWNED_STATE | 0x44 | field1 byte：0=状態、1〜8=所有識別子、9〜10=進行offsetの下位／上位 |
| OWNED_RECOVER | 0x45 | 照会した所有識別子8 bytes + 期待するoffset2 bytes |

状態は0x70=空き、0x71=新方式で進行中、0x72=新方式で30秒以上進行なし、0x73=旧方式で更新中、0x74=新方式でCOMMIT済み。状態照会の応答byteは値そのものなので、tokenの1〜3をエラーとして解釈しない。照会は保存・出力・期限を変更しない。

新方式対応の確認はSTATE field0で行う。unsupported(1)だけを旧ファームと扱い、その他の未知応答・timeoutは保存開始前に終了する。旧ファームは従来方式へフォールバックする。既存ファームは未対応命令への応答時に音を止めることがあり、照会が出力を変えない保証は新ファームに対するもの。保存操作の上書き確認後に照会する。

所有識別子はブラウザで保存ごとに生成するランダム64bit（全0は予約）。認証・悪意のある送信元への防御ではなく、古い送信元との偶発的な衝突防止を目的とする。識別子は作品ファイルへ保存せず、診断ログにも生byteを出さない。1回の保存の通信数はsequenceの256周回未満に収まる。

BEGIN受理・正常なDATA受理でボードの最終進行時刻を更新する。30秒以上進行がないとDATA・COMMITの再開は拒否するが、自動ABORTはしない。期限は32bitの差分で判定し、メインループで期限切れを保持する。時刻が一周しても期限内へ戻らないことをテストする。元の所有者のABORTは期限後も許す。識別子が異なる送信は常に拒否する。ボード再起動後は更新状態を保持せず、有効bankから再開する。

ブラウザは状態・識別子・offset・状態を順に照会する。照会中の変化は再確認を案内し、解除しない。期限切れの場合だけ利用者へ確認し、キャンセルは照会のみで終了する。解除時はボード上で「今も更新中、新方式、識別子一致、offset一致、最終進行から30秒以上」を再照合する。いずれか違えば解除を拒否する。解除ACKが不明なら再送・新BEGINはしない。解除成功後に空き状態を読み直してから新しい所有者で保存する。

照会後に元の所有者が進行した場合は、offsetまたは期限の再照合で解除を拒否する。解除後に元の所有者が再開した場合は、新しい識別子と一致しないためDATA・COMMIT・ABORTを拒否する。新方式の保存中には、旧方式のBEGIN・DATA・COMMIT・ABORTも入口で拒否する。旧方式同士の競合や旧方式の残留復帰は対象外で、通常再接続を案内する。

COMMIT済みの場合は最後の識別子とoffsetを保持する。新方式は正常ACKを受けた場合も、ACK不明時も、識別子・完了offset・保存先の一致を確認してから成功とする。別送信元のCOMMITや、新しいBEGINで状態が変わっていれば成功と断定せず、再送しない。

ただし保存以外の通信も応答キャッシュへ影響する制約は残る。異なるoriginの通信や不正な送信をUSB全体で排他するものではなく、進行中の保存を別画面から操作しない案内は引き続き必要。

試作ビルドはFlash13,184 bytes／上限14,336（空き1,152）、静的RAM460 bytes。基準12,416／440からFlash768・RAM20増。スタック使用量は静的RAMに含まれず、ラッパーの正規化バッファ24 bytes等も使う。ソース・bin・build-info・ZIPを同時更新して検証するが、実機検証前に公開しない。

### ブラウザのみでの待ち時間短縮の試作

新方式のBEGIN／DATA／COMMITだけ、通常Input応答が250ms届かなければGET_REPORTを1回読むようにした。250msは処理完了を仮定する時間ではなく、読み取り確認を始める目安。通常応答が先に届けば追加通信はしない。早期確認中も同じ通常受信Promiseを保持し、古いキャッシュや非対応なら、元の10秒／2秒の期限内で遅れて届くACKを待つ。最終期限でも応答不明なら従来どおり最終キャッシュ確認と後処理へ進む。キャッシュのmagic・version・command・sequence・長さ照合は維持する。

早期GET_REPORTそのものが1秒で時間切れになった場合は、ブラウザ内に未完了の読み取りが残り得るため、新しいDATA／COMMITへ進めず失敗経路へ移る。旧方式には早期確認を追加しない。受信・照合処理を`standaloneResponseProbe`へ分離し、早期確認と遅延Inputの競合、古いキャッシュ、非対応、GET_REPORT自体の時間切れ、拒否ACK、旧方式の待機時間維持をテストする。速くなったかの実機測定はこれからであり、物理的な応答喪失原因の解消ではない。

これはブラウザのみの変更。ファームbinのSHA-256は引き続き018b0ebf…、13,184 bytes、空き1,152 bytes、静的RAM460 bytesから変えない。実機の再フラッシュは不要。
