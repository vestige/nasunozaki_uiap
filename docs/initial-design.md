# UIAPduino Browser Studio：初期構想

作成日: 2026-08-29

位置づけ: 初期構想。現在の確定仕様は `spec.md` を参照する。

## 1. 目的

UIAPduinoをブラウザからプログラミング、実行、保存、書き込みできる統合開発環境を作る。小学生向けワークショップは、その操作性と安定性を検証する最初の実証実験とする。

目指す体験は次のとおり。

1. USBでUIAPduinoをつなぐ
2. 画面でブロックを組み立てる
3. 「じっこう」ボタンを押す
4. LEDなどがすぐに動く
5. ブロックを直して何度でも試す

プログラミング言語やマイコンの書き込み手順を先に覚えるのではなく、「考える、動かす、気づく、直す」という流れを短い時間で繰り返せる教材にする。

## 2. 対象と利用条件

- 主な対象: 小学校3〜6年生
- 形式: 60〜90分程度の対面ワークショップ
- 端末: PCまたはChromebookを第一候補とする
- ブラウザ: デスクトップ版Chrome／Edge
- 配信: GitHub Pages（HTTPS）
- 接続: USB接続したUIAPduinoとのWebHID通信
- 操作補助: 講師1名と数名ごとのサポーターを想定

SafariとFirefoxはWebHIDを利用できないため、初期対象外とする。ワークショップで使用する端末、USBケーブル、ブラウザの組み合わせは事前に実機確認する。

## 3. 採用する実装方針

### 3.1 最初は「命令転送方式」にする

最初のバージョンでは、Blocklyから生成した処理をブラウザで管理し、簡単な命令としてWebHID経由でUIAPduinoへ送る。

```text
Blocklyのブロック
      ↓
ブラウザ内の実行エンジン
      ↓ 小さな命令
WebHID通信
      ↓
UIAPduino教育用ランタイム
      ↓
LED・ボタン・センサーなど
```

UIAPduinoにはワークショップ前に教育用ランタイムを書き込んでおく。参加者が実行するたびにマイコンのファームウェア全体を書き換えることはしない。

この方式を採用する理由は次のとおり。

- 実行開始までの待ち時間を短くできる
- コンパイラのダウンロードやサーバー処理が不要
- 書き込みモードへの切り替えで参加者が迷わない
- USB切断や操作ミスによる書き込み失敗を避けやすい
- 実行中のブロックを画面上で光らせられる
- 停止、1ステップ実行、やさしいエラー表示を実装しやすい

### 3.2 JavaScriptコードを直接ボードへ送らない

CH32V003上でJavaScriptを直接実行する設計にはしない。Blocklyが生成するJavaScriptはブラウザ側の制御に使い、UIAPduinoには固定長の命令やデータを送る。

初期実装では、任意のJavaScript文字列を`eval`で実行する方式も避ける。Blocklyのワークスペースを安全な中間命令列へ変換し、許可した命令だけを実行する。

中間命令の例:

```json
[
  { "op": "LED_SET", "value": 1 },
  { "op": "WAIT", "milliseconds": 500 },
  { "op": "LED_SET", "value": 0 }
]
```

### 3.3 ファームウェア書き込みは第2段階以降

将来、「ブラウザを閉じても単独で動く」体験が必要になった場合は、次の順で拡張を検討する。

1. 命令列をUIAPduino側の不揮発領域へ保存し、教育用ランタイムが単独実行する
2. ブラウザ内またはサーバーでネイティブバイナリを生成する
3. WebHID対応ブートローダー経由でファームウェアを書き込む

ワークショップの安定性を優先し、初期版ではブートローダーやファームウェアの書き換えを参加者の通常操作に含めない。

## 4. システム構成

### 4.1 Webアプリ

- Blockly: ブロックの表示、接続、保存
- Block definitions: 子ども向けの専用ブロック
- Program compiler: ワークスペースから中間命令列への変換
- Execution engine: 命令の順次実行、停止、実行位置通知
- WebHID adapter: 接続、再接続、送受信、タイムアウト処理
- Simulator adapter: UIAPduino未接続時の画面内シミュレーション
- Lesson controller: 課題、ヒント、利用可能ブロックの切り替え
- Local storage: プログラムと進行状況の端末内保存

通信先の違いを上位層から隠すため、実機とシミュレーターは同じインターフェースを持たせる。

```ts
interface BoardAdapter {
  connect(): Promise<void>;
  disconnect(): Promise<void>;
  execute(command: Command): Promise<Result>;
  stop(): Promise<void>;
  getState(): BoardState;
}
```

### 4.2 UIAPduino教育用ランタイム

初期ランタイムの役割は次のとおり。

- WebHIDから命令を受信する
- 命令番号と引数を検証する
- GPIOなどを操作する
- 成功、失敗、入力値をブラウザへ返す
- 停止命令を優先して処理する
- 接続が切れた際に安全な状態へ戻す

長時間の待機をファームウェア内のブロッキング処理にせず、可能な限りブラウザの実行エンジンで管理する。これにより停止操作への反応を保つ。

### 4.3 初期通信プロトコル案

UIAPduinoのHIDレポートサイズに合わせ、バイナリの小さなパケットとして設計する。正確なサイズとReport IDは、対象ファームウェアおよび実機調査後に確定する。

要求パケット案:

| 項目            | 内容                          |
| --------------- | ----------------------------- |
| protocolVersion | プロトコル互換性確認用        |
| sequenceId      | 要求と応答の対応付け          |
| opcode          | LED、GPIO、入力取得などの命令 |
| payloadLength   | 引数の長さ                    |
| payload         | 命令の引数                    |

応答パケット案:

| 項目            | 内容                                 |
| --------------- | ------------------------------------ |
| protocolVersion | プロトコルバージョン                 |
| sequenceId      | 対応する要求番号                     |
| status          | 成功、未対応、不正値、内部エラーなど |
| payloadLength   | 戻り値の長さ                         |
| payload         | センサー値など                       |

次の安全対策を含める。

- 対応VID/PIDとHID collectionを限定する
- プロトコルバージョンを接続時に確認する
- すべての命令にタイムアウトを設ける
- 範囲外のピン、角度、時間などを双方で拒否する
- 同一命令の二重実行を防ぐためsequence IDを使う
- 切断、停止、エラー時はLEDや出力を安全な状態へ戻す

## 5. 子ども向け画面設計

### 5.1 基本レイアウト

```text
┌──────────┬────────────────────┬────────────┐
│ ブロック │  ブロックを組む場所 │ 実機／見本  │
│ 一覧     │                    │ 課題・ヒント│
└──────────┴────────────────────┴────────────┘
│ つなぐ       じっこう       とめる       │
└───────────────────────────────────────┘
```

スマートフォンは初期対象外とし、1024px程度以上の横幅を基本とする。Chromebookの一般的な画面で、横スクロールなしに主要操作が収まることを確認する。

### 5.2 表現方針

- 漢字には必要に応じてふりがなを付ける
- 「接続」「実行」より「つなぐ」「じっこう」のような行動語を使う
- ピン番号ではなく「ボードのLED」「右のボタン」など部品名で示す
- 成功、実行中、困っている状態を色だけでなく形と文でも示す
- 危険な操作や高度なブロックは通常画面に出さない
- エラー番号ではなく、次に試す行動を表示する

エラー表示例:

- 「ボードが見つからないよ。USBケーブルをさして、もう一度『つなぐ』を押してね」
- 「ほかの画面がボードを使っているかも。ほかの教材ページを閉じてみよう」
- 「ボードとの通信が止まったよ。USBをさし直してみよう」

### 5.3 初期ブロック

最初から多数のブロックを見せず、課題ごとに使用可能なものを増やす。

MVPで提供するブロック:

- スタートしたとき
- ボードのLEDをつける
- ボードのLEDを消す
- ○秒待つ
- ○回くり返す
- もしボタンが押されていたら

候補となる次のブロック:

- 明るさを調べる
- 音を鳴らす／止める
- サーボを○度にする
- 数、比較、変数

## 6. ワークショップの初期教材

60〜90分の流れを次のように想定する。

1. 完成済みプログラムでLEDを点灯し、最初の成功を得る
2. 待ち時間を変え、結果との関係を試す
3. LEDを複数回点滅させる
4. 「くり返す」ブロックでプログラムを短くする
5. ボタン入力を使って動きを変える
6. 信号機や合図ライトを自由制作する
7. 作品と工夫した点を発表する

講師用には、端末確認表、予備ボード、予備ケーブル、接続トラブル時の復旧手順、各課題の完成例を別途用意する。

## 7. GitHub Pagesへの公開設計

Webアプリは静的ファイルとしてビルドし、GitHub ActionsからGitHub Pagesへ公開する。

```text
mainへpush
   ↓
GitHub Actionsでテストとビルド
   ↓
静的ファイルをPagesへデプロイ
   ↓
https://<user>.github.io/nasunozaki_uiap/
```

実装上の注意:

- リポジトリ配下のURLでも動くよう、公開ベースパスを設定する
- WebHID通信はブラウザからUIAPduinoへ直接行い、サーバーへ転送しない
- Blocklyや教材画像は可能な限りビルド成果物に同梱する
- 子どもの氏名や作品データをサーバーへ収集しない
- プログラムの自動保存は初期版ではlocalStorageを使う
- Service Workerによるオフライン対応はMVP後に検討する
- WebHID非対応ブラウザでは、理由と推奨ブラウザを最初に案内する

### 8.1 React Componentの設計ルール

- `App.tsx`はページ全体の組み立てに限定し、通信処理や大きな表示ブロックを直接持たせない
- ヘッダー、接続手順、接続操作、デバイス結果、各診断操作を責務ごとのComponentへ分ける
- Component名とファイル名を一致させ、原則として `features/<feature>/components/` 以下へ配置する。複数機能で共有するものだけルートの `components/`へ置く
- 機能ごとに `components`（表示）、`hooks`（状態と処理の調整）、`utils`（Reactに依存しない処理）、`types`（共有契約）へ分ける。空の分類フォルダは先回りして作らない
- WebHID固有の型は `features/device/types/`、定数・packet生成・通信処理は `features/device/utils/`へ分離し、表示ComponentからWebHID APIを直接呼ばない
- 1ファイルに表示、状態調整、データ変換など複数の変更理由が集まったら分割する。行数だけを基準にせず、名前で責務を説明できる境界を優先する
- 同じ画面だけで使う小さな表示は過度に分割せず、役割を名前で説明できる単位を目安にする
- 自動テストは実装ファイルの隣へ混在させず、`src/__tests__/<feature>/`に配置する。純粋なutilsを中心に、実機なしで安全条件を確認する
- 配信はGitHub Pagesを正とし、`.openai/hosting.json`は使用しない。将来別のホスティングへ移行すると決めた場合にだけ、そのサービス固有設定を追加する

### 8.2 TanStack Queryによる状態管理

WebHIDデバイスはブラウザ外部で状態が変化し、接続、読み取り、送信はいずれも非同期処理である。この外部状態と処理状態をTanStack Queryで管理する。

- アプリのルートを `QueryClientProvider`で囲む
- 接続デバイス、Feature Report、診断結果は安定したquery keyでキャッシュする
- 接続、読み取り、送信は `useMutation`へまとめ、`isPending`と`isError`をUIへ反映する
- USBの `disconnect` イベントはWebHID層で受け、Query Clientの対象キャッシュを更新する
- WebHIDの状態同期を目的とした `useEffect`と、非同期結果を複製するための `useState`は使わない
- Component内だけで完結する開閉状態や入力途中の値など、外部状態ではない一時的UI状態までTanStack Queryへ入れない。必要時は用途に合うReactの局所状態を選ぶ
- Query keyと既定設定は1か所に集約し、通信処理と表示処理を分離する
- バイナリpacketの組み立ては純粋関数にし、実機なしでバイト位置と安全条件を自動テストする
- packet内の入力位置と結果位置は別の定数・検証値として扱い、同じ値を誤読しないテストを置く
- GitHub Pagesの公開前にTypeScript buildとprotocol testの両方を実行する
- 診断ログも安定したquery keyで管理し、各非同期操作の成功、注意、失敗と主要な診断値を記録する

TanStack Queryは本来、非同期に取得・更新される外部状態を取得、キャッシュ、同期するためのライブラリである。この役割に沿って採用し、あらゆるReact状態を機械的に置き換える用途にはしない。

参考: [TanStack Query React Overview](https://tanstack.com/query/latest/docs/framework/react/overview)

### 8.3 診断ログの設計ルール

- Phase 0の技術的な通信ログは、子ども向けの通常操作画面とは分離した専用Componentで表示する
- 時刻、レベル、操作名、人が読める説明、必要最小限の診断値を1件として記録する
- 接続、切断、Feature Report、RAM往復、チップ識別、dry-run、flash preflightを記録対象とする
- ログはTanStack Queryのメモリーキャッシュだけに保持し、ページ再読み込みを越えて保存しない
- サーバー送信、自動ファイル保存、個人情報の記録は行わない
- 利用者が調査結果を共有できるよう全文コピーを提供し、任意に消去できるようにする
- flashの実行許可や操作履歴の正本にはせず、安全判定は診断結果の型と実行前検証で行う
- 実機状態を変更する調査操作は警告色と確認ダイアログを使い、開始、途中完了数、再読み取り結果をログへ残す

## 9. 開発段階

### Phase 0: 実機調査

- 使用するUIAPduinoの型番とファームウェアを固定する
- VID、PID、Report ID、送受信可能サイズを確認する
- Chrome、Edge、Chromebookで接続試験を行う
- LEDとボタンの物理的な割り当てを確認する
- 破壊的操作へ進む前に、読み取り専用RAM stubで実行・応答経路を確認する
- 書き込みpacketは最初にオフライン生成と自動テストだけを行い、対象範囲と復旧手順を確定してから実機送信を有効化する
- 実行マジックを含むpacketは型で明示し、WebHID送信層へ暗黙に渡せない構造にする
- flash操作は `unlock → block退避 → erase → write → read-back verify`を1つの手順として設計し、途中失敗時は再接続後に検証から再開する
- 部分書き込みは64バイトblockを必ず退避してからmergeし、未変更部分を消去で失わないようにする
- 書き込み計画と実機送信を別の型・層に分離し、計画生成だけでは実機状態を変更できないようにする
- binファイルの確認画面はdry-run専用とし、ファイル内容をサーバーへ送らず、実機送信操作も同じ画面に置かない
- dry-runの成功表示は「計画生成成功」と明記し、flash書き込み成功と混同しない
- 確認専用の操作は情報色、実機の破壊的操作は警告色で表し、色の意味を混同しない
- unlock・erase・write用の実行可能packetはProtocol層でのみ生成し、Device adapterが明示的に許可されるまで送信できない状態を保つ
- flash操作前にロック状態とread protectionを読み取り専用で確認し、想定外の状態では処理を停止する
- unlockのような状態変更では画面に表示済みの結果だけに依存せず、実行直前にも同じ安全条件を通信層で再検証する
- unlock、erase、writeは別々の段階として有効化し、前段の実機結果と復旧性を記録するまで次段の送信経路を作らない
- erase前には対象64バイトblockを必ず読み取り、hex dumpとCRC32を基準値としてブラウザ内に保持する
- flash退避データは個別のQuery keyで管理し、接続解除または再接続時に破棄して別デバイスのデータと混在させない
- 破壊的操作へ進む前に退避データをbinファイルとして端末へ保存し、同じセッション内で再読込して容量、CRC32、全バイトの一致を確認する
- 復旧用ファイル名には対象addressとCRC32を含め、どのblockの基準値か判別できるようにする
- unlock後はUSBを物理的に再接続しても状態が継続する場合があるため、再接続後に必ずCTLRを読み直し、ロック状態を推測しない
- unlock済みの案内は操作目的に応じて分け、通常の調査では再接続を促し、保存済みbinからの復旧作業ではread protectionなしを確認して直接復元へ案内する
- eraseと元データ復元は別々の利用者操作にせず、preflightから最終verifyまでを1つのtransactionとして実行する
- 破壊的処理の開始後は、途中エラーでも現在値を確認して復旧を試み、復旧確認の成否を通常エラーと区別して残す
- transactionは先に注入可能なadapterを使って実機なしで全順序と失敗経路を検証し、検証完了までWebHID送信層や画面へ接続しない
- 破壊的な実機確認ボタンは、同一接続内のunlock、退避、PC保存ファイルの完全一致確認が揃った場合だけ有効にする
- ボタン文言は内部用語の`erase`だけにせず、「先頭64バイトを消去して元に戻す」のように実際の動作を日本語で示す
- eraseと復元の各段階を診断ログへ残し、復旧未確認時はUSBを抜かずにログを確保する行動を画面で案内する
- 実機で破壊的操作が想定外の結果になった場合は同じ操作を直ちに停止し、原因確認と既存バックアップからの復旧だけをUI上で許可する
- CH32V003の64バイトpage write前には、page programming mode設定とbuffer resetを必須の独立手順として実行・検証する
- 復旧成功は書き戻し要求の完了だけで判定せず、保存済みbinと読み戻した全バイトの一致およびCRC32の一致で判定する
- 破壊的packetの参照実装照合はrevisionを記録し、stub全体、引数位置、未使用領域、実行マジックを自動テストで固定する
- WebHID応答はReport IDの有無による127バイト／128バイトの両形式をテストし、完了フラグの位置ずれを防ぐ
- flash異常の切り分けは破壊的操作を再試行する前に、CTLR、STATR、OBTKEYRを読み取り専用で取得し、生値と主要フラグを診断ログへ残す
- 読み取り専用の追加診断も独立したTanStack Query keyとmutationで管理し、接続解除または再接続時に古い結果を破棄する
- flash statusの安全判定は生のSTATRも記録し、主要フラグが未検出でも破壊的操作の再開条件とはせず、観測できた範囲を明記する

完了条件: ブラウザの最小ページからLED命令を送り、応答を受信できる。

### Phase 1: 画面プロトタイプ

- [x] Blockly画面を表示する
- [x] LED、待つ、繰り返しブロックを実装する
- [x] 画面内シミュレーターを動かす
- [x] 実行中ブロックのハイライトと停止を実装する
- [x] プログラムを端末内へ自動保存する
- [x] 作品をファイルへ保存し、別の端末で読み込めるようにする

2026-09-08に最初のプロトタイプを実装した。workspaceの変更は型付き中間命令列へ変換し、TanStack Queryへ保持する。シミュレーターの実行と停止もmutationで管理し、任意JavaScriptの `eval`や実機送信は行わない。BlocklyのDOM lifecycleに必要な処理はReact 19のcallback refで閉じ、コンポーネントの汎用的な状態管理へ `useState`や `useEffect`を持ち込まない。

Blocklyの永続化はworkspace全体を公式serialization APIで保存し、保存形式にversionを付ける。壊れたJSONや未対応versionは復元せず初期例を使用する。TanStack Queryは編集中の状態と保存結果表示を管理し、`localStorage`への読み書きは独立したpersistence moduleへ分離する。操作ボタン、Blockly編集領域、LEDシミュレーターも役割ごとのコンポーネントに分ける。

作品の持ち帰りと端末間移動には、Blockly workspaceを含むversion付き `.uiap.json`ファイルを使う。読み込み時は専用format、version、workspace、保存日時、1MBの容量上限を検証し、現在のworkspaceを置き換える前に利用者へ確認する。ファイル内容はブラウザ内だけで扱い、サーバーへ送信しない。

シミュレーターの実行順序はUIから独立したruntime moduleへ置き、LED更新、ハイライト、待機をadapterとして注入する。中間命令が保持するblock IDを使って実行位置を示し、繰り返し内も同じ経路で処理する。停止は `AbortSignal`で伝播し、待機中でもLEDとハイライトを安全な表示へ戻す。

完了条件: UIAPduinoがなくても、最初の点滅教材を最後まで体験できる。

- [x] 中間命令列を実行する共通 `BoardAdapter`境界を実装する

- [ ] ランタイム用VID/PIDとWebHIDのReport IDなし（0）の扱いを実機で確認する
- [x] `0x1209:0xD004`専用の読み取り診断画面を実装する
- [ ] 教育用ランタイムの実機Adapterを実装する
- [x] 実機Adapterのtransport非依存なtransaction処理を実装する
- LED出力とボタン入力を実装する
- 切断、再接続、タイムアウトを扱う
- GitHub Pagesへ自動公開する

完了条件: 初めて操作する子どもが、補助を受けながら10分以内にLEDを点滅できる。

`BoardAdapter`はLED操作と待機だけを受け持ち、Blockly block IDのハイライトなど画面固有の処理は `ExecutionObserver`へ分離する。これによりシミュレーターと実機で命令解釈を共有し、実機通信層がBlockly APIへ依存しない構造にする。

UIAPduino HID Arduino core `1.2.14`では、ブラウザからEP0 Feature Reportを最大32バイト受信し、ボードからEP1 Input Reportを8バイト送信できる。この制約に合わせ、初期プロトコルは `UIAP`識別子、version、command、8bit sequence、1byte payload/statusからなる8バイト固定長とする。内蔵LEDはArduino pin 2を使う。

`firmware/workshop-runtime/workshop-runtime.ino`へLED命令の受信、入力検証、LED更新、応答を実装し、core `1.2.14`、WebHID Only、`-Os` + LTOでコンパイルする。2026-09-09の結果はFlash 4004 / 16384 bytes、RAM 172 / 2048 bytesである。ブラウザの実機Adapterと書き込み導線は、ランタイムdescriptorを実機確認するまで接続しない。

接続時のHID descriptorにInputまたはOutput Reportがあれば教育用ランタイム候補、Input/Output ReportがなくFeature Report `0xAA`だけならbootloaderと分類する。この分類はdescriptorから観測できる範囲の案内であり、ランタイム対応の確定や命令送信許可には使わない。

ランタイム診断は `features/runtime/`内に型、WebHID処理、TanStack Query hook、表示Componentを分離する。bootloader用device stateとは別のquery keyを使用し、片方の切断が他方の表示を消さないようにする。初回の実機確認では命令送信を有効化せず、descriptorの観測結果を先に固定する。

ランタイム実機Adapterは `RuntimeTransport`境界へ8バイト命令の送受信だけを依頼する。Adapter側でsequence一致、status、timeout、停止を処理し、WebHIDのReport IDやevent listenerはtransport実装へ閉じ込める。実機descriptorが確定するまでtransportを画面へ接続しない。
Adapterの可読性を保つため、時間に関するPromise処理は `runtimeTiming.ts`へ分ける。Adapter本体にはLED transactionとsequence管理を残し、時間制御のテストも別ファイルに配置する。

Blocklyなど内部に独自の描画幅を持つComponentは、grid itemへ `min-width: 0`相当を指定してページ全体の横はみ出しを防ぐ。見出しと操作群はdesktop幅まで縦並びを維持し、操作可能領域と本文を潰さない。
BlocklyはCSS幅の変更だけでは内部SVGの寸法が更新されないため、workspace Component内の `ResizeObserver`で `Blockly.svgResize()`を実行する。observerと予約済みanimation frameはcallback refのcleanupで破棄する。
独立したカードSection同士は負のmarginで重ねない。装飾的な重なりを使う場合も、同一Section内に閉じて後続機能の操作領域を覆わないようにする。

## 10. テスト方針

### 自動テスト

- 各ブロックから期待する中間命令が生成される
- 繰り返しや条件分岐が上限を超えて暴走しない
- 停止操作で次の命令を送らない
- WebHIDパケットのエンコード／デコードが一致する
- 切断、タイムアウト、不正応答を正しい表示へ変換する
- GitHub Pagesのサブパスでアセットを読み込める

### 実機テスト

- 対象OS／ブラウザごとの接続と再接続
- USBを途中で抜いた場合の復旧
- 連続実行や停止を繰り返した場合の安定性
- 複数タブで接続しようとした場合の案内
- 低速または不安定なネットワーク環境での初回表示

### 子どもによる操作テスト

正解率だけでなく、次の点を観察する。

- 「つなぐ」から実行まで自力で進めたか
- ブロックの名前から結果を予想できたか
- 失敗したときに自分で直そうとしたか
- エラー表示を読んで次の操作ができたか
- 文字の大きさや操作対象が見つけやすかったか

## 11. MVPの範囲外

初期版では次を行わない。

- Safari、Firefox、スマートフォン対応
- ユーザーアカウントとクラウド保存
- 子どもの個人情報や利用履歴の収集
- Arduino C/C++の自由入力とコンパイル
- 通常操作からのブートローダー書き換え
- 任意のピンや任意のHIDデバイスへのアクセス
- 複数の異なるUIAPduinoモデルへの同時対応
