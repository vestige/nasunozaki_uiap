# Blockly作品のボード単独実行

Issue #35で、Blockly作品をUIAPduinoへ保存し、ブラウザやUSB接続なしで実行する方式を検証する。

## 1. 最初のゴール

最初のフィジビリティ確認は、次の作品だけを対象とする。

```text
ずっと
    LEDをつける
    500ミリ秒まつ
    LEDをけす
    500ミリ秒まつ
```

ブラウザで作品を書き込み、USBを外して再給電した後も内蔵LEDが点滅すれば成功とする。最初からタクトスイッチ、NeoPixel、変数、任意のBlocklyブロックには対応しない。

## 2. 採用する検証方式

完成済みの教育用ランタイムへ小さな命令実行器を追加し、ファームウェア内に固定サイズの作品領域を予約する。ブラウザはBlocklyの安全な中間命令を小さなbytecodeへ変換し、空の作品領域を置き換えたファームウェアイメージを既存bootloader経由で書き込む。

```text
Blockly workspace
      ↓
安全な中間命令列
      ↓
単独実行用bytecode
      ↓
完成済みランタイムbinの作品領域へ埋め込む
      ↓
既存bootloaderで書き込み・verify
      ↓
再起動後にランタイムがbytecodeを実行
```

この方式では利用者のブラウザでC/C++をコンパイルしない。許可済みの命令だけを符号化し、任意コード、任意アドレス、任意GPIOを作品から実行できないようにする。

## 3. 他方式との比較

### 作品ごとにネイティブファームウェアをビルドする

BlocklyからC/C++を生成し、Web Buildで作品ごとのbinを作る方式。最終的なコードサイズや速度には有利だが、最初の検証にはcompilerサービス、生成コードの安全確認、失敗時の案内が必要になる。ネット接続なしのワークショップでも使いにくいため、Issue #35の最初の方式にはしない。

### 通常動作中に作品だけをflashへ保存する

WebHIDでランタイムへbytecodeを送り、ランタイム自身がflashを書き換える方式。毎回bootloaderへ入り直さず更新できる可能性があるが、実行中コードと同じflashを安全に消去・更新する設計が必要になる。過去のerase調査も未解決のため、最初の検証では行わない。

### bootloaderでランタイムと作品を一緒に書く

既存の書き込み・64バイト単位verify・再起動経路を再利用できる。失敗時も現在配布している空の教育用ランタイムを書き直して復旧できるため、最初の方式として採用する。

## 4. 作品形式の設計条件

- magic、形式version、payload長、checksumを持つ
- 作品領域は固定長とし、ランタイム本体と重ならないことをbuild時に確認する
- 空または不正な作品は実行せず、LEDとNeoPixelを安全な消灯状態にする
- 未知のopcode、範囲外の引数、途中で切れた命令は実行しない
- Blockly側で命令数、byte数、入れ子の深さ、待機時間に上限を設ける
- 最初のopcodeは内蔵LED、待機、繰り返し、終了に限定する
- 後から条件分岐、ボタン、NeoPixel、変数を追加できるversion付き形式にする
- `blockId`などブラウザ表示専用情報はボードへ保存しない

最初の検証では作品領域を1024バイト、headerを16バイト、payloadを最大1008バイトとする。Flash/RAM実測後に、この領域を維持できるか再確認する。

headerは次の形式とする。複数byteの数値はlittle endianで格納する。

| offset | 長さ | 内容 |
| ---: | ---: | --- |
| 0 | 4 | magic `UIBP` |
| 4 | 1 | 形式version。初期値は`1` |
| 5 | 1 | flags。bit 0は起動時の自動実行 |
| 6 | 2 | payload長 |
| 8 | 2 | payloadのCRC-16/CCITT-FALSE |
| 10 | 6 | 予約。version 1ではすべて`0` |

最初のopcodeは次のとおりとする。

| opcode | 命令 | 引数 |
| ---: | --- | --- |
| `0x00` | 終了 | なし |
| `0x01` | 内蔵LED | 状態1バイト。`0`消灯、`1`点灯 |
| `0x02` | 待機 | ミリ秒2バイト。`0`〜`5000` |
| `0x10` | 回数指定の繰り返し | 回数1バイト、body長2バイト、body |
| `0x11` | ずっと | body長2バイト、body |

繰り返し回数は1〜20、構造の入れ子は8段までとする。version 1のencoderはタクトスイッチ、NeoPixel、変数、論理演算を拒否し、未対応命令を別のopcodeへ読み替えない。

## 5. 起動と停止

- 有効な作品があれば、起動後に自動実行する
- 有効な作品がなければ、現在と同じWebHID教育用ランタイムとして待機する
- 単独実行中も、有限の待機へ分割してUSB処理へ復帰できる設計を優先する
- 電源断は任意の命令位置で起こるものとして扱い、再起動時は作品の先頭から始める
- 実行エラー時は出力を消灯し、作品の実行を停止する

ブラウザからの停止方法や、単独実行中にも通常のWebHID命令を受け付けるかは、最初のLED点滅確認後に決める。

## 6. 書き込みの安全境界

- 対象はbootloaderのVID:PID `0x1209:0xB803`だけに限定する
- 書き込み前に、ベースとなる完成済みランタイムのSHA-256を照合する
- 作品を埋め込める場所は、ビルド時に用意した一意な予約領域だけに限定する
- 生成後のファームウェアサイズが16KiBを超える場合は書き込まない
- 書き込み後は既存処理と同様に64バイト単位でverifyする
- 作品書き込みはUIAPduino上の現在のプログラムを置き換えることを明示する
- 配布中の空ランタイムを書き直せば復旧できる状態を維持する

## 7. 検証の順序

1. TypeScriptで最小bytecode encoderと入力検証を作る
2. ランタイムに空の作品領域と最小interpreterを追加する
3. 空作品と不正作品で安全に待機することを自動テスト・buildで確認する
4. LED点滅bytecodeを埋め込んだbinをローカル生成し、hashと領域外不変を確認する
5. 実機へ書き込み、USBを外した再給電後も点滅することを確認する
6. ブラウザ画面へ「UIAPduinoへ作品を書き込む」導線を追加する
7. 既存の繰り返し、タクトスイッチ、NeoPixelの順に対応範囲を広げる

変数と論理ブロックはIssue #41で扱う。Issue #35で確定したbytecodeと実行器の制約を前提に設計する。

## 8. 最初の完了条件

- [ ] LED点滅作品を安全なbytecodeへ変換できる
- [ ] 作品入りbinで変更される範囲が予約領域だけである
- [ ] 書き込みとverifyに既存bootloader経路を使える
- [ ] USBを外して再給電してもLED点滅が始まる
- [ ] 不正な作品では出力を消灯して停止する
- [ ] 空ランタイムへ戻す復旧手順を確認できる
- [ ] Flash/RAM使用量と作品の最大byte数を記録する
