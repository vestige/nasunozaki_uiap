# Blockly作品のボード単独実行

Issue #35で、Blockly作品をUIAPduinoへ保存し、ブラウザやUSB接続なしで実行する方式を検証する。

## 1. 最初のゴール

最初のフィジビリティ確認は、次の作品だけを対象とする。

```text
ずっと
    LEDをつける
    500ミリ秒まつ
    LEDをけす
    500ミリ秒まつ
```

ブラウザで作品を書き込み、USBを外して再給電した後も内蔵LEDが点滅すれば成功とする。最初からタクトスイッチ、NeoPixel、変数、任意のBlocklyブロックには対応しない。

## 2. 本来の製品方式

子どもがボタンを押しながらUSBを接続する手順は、作品を書き換えるたびには行わせない。教育用ランタイムを一度導入した後は、通常動作モード（VID:PID `0x1209:0xD004`）で接続したまま、ブラウザから作品bytecodeだけを書き換える。

```text
Blockly workspace
      ↓
安全な中間命令列
      ↓
単独実行用bytecode
      ↓ WebHID（通常動作モード）
未使用側の作品bankへ分割転送・検証
      ↓
最後に有効化し、次回起動から実行
```

ランタイム本体と作品は別領域にする。Flash末尾2KiBを固定予約し、1KiBずつのbank A/Bとして使う。現在有効なbankを残したまま未使用bankを消去・更新し、全byteの長さとCRCが一致した後にだけ新しいbankを有効とみなす。転送中のUSB抜去や電源断では、直前の正常な作品を引き続き使う。

ランタイム領域は14KiBを上限としてlinkerで保護し、作品書き込み命令からランタイム領域や任意アドレスを指定できないようにする。作品の保存先はbank番号と連番からランタイム側が決める。

通常接続で作品を書けるランタイムを最初に導入するときだけ、従来の書き込みモードが必要になる。以後の作品作成では不要にする。

## 3. 検証済み代替案のメモ

2026-10-02のフィジビリティ確認では、次のbootloader方式を実装した。この方式は単独実行できることを確認するための安全な代替・復旧経路として残すが、子ども向けの通常導線にはしない。

完成済みの教育用ランタイムへ小さな命令実行器を追加し、ファームウェア内に固定サイズの作品領域を予約する。ブラウザはBlocklyの安全な中間命令を小さなbytecodeへ変換し、空の作品領域を置き換えたファームウェアイメージを既存bootloader経由で書き込む。

```text
Blockly workspace
      ↓
安全な中間命令列
      ↓
単独実行用bytecode
      ↓
完成済みランタイムbinの作品領域へ埋め込む
      ↓
既存bootloaderで書き込み・verify
      ↓
再起動後にランタイムがbytecodeを実行
```

この方式では利用者のブラウザでC/C++をコンパイルしない。許可済みの命令だけを符号化し、任意コード、任意アドレス、任意GPIOを作品から実行できないようにする。

## 4. 他方式との比較

### 作品ごとにネイティブファームウェアをビルドする

BlocklyからC/C++を生成し、Web Buildで作品ごとのbinを作る方式。最終的なコードサイズや速度には有利だが、最初の検証にはcompilerサービス、生成コードの安全確認、失敗時の案内が必要になる。ネット接続なしのワークショップでも使いにくいため、Issue #35の最初の方式にはしない。

### 通常動作中に作品だけをflashへ保存する（採用）

WebHIDでランタイムへbytecodeを送り、ランタイム自身が予約済みflashだけを書き換える方式。毎回bootloaderへ入り直さず更新できる。固定領域、二重bank、範囲検査、CRC、電源断時の復旧を先に実装し、過去に問題が起きた先頭pageやランタイム本体は消去対象にしない。

### bootloaderでランタイムと作品を一緒に書く（検証済み代替案）

既存の書き込み・64バイト単位verify・再起動経路を再利用できる。失敗時も現在配布している空の教育用ランタイムを書き直して復旧できるため、最初のフィジビリティ確認に採用した。

## 5. 作品形式の設計条件

- magic、形式version、payload長、checksumを持つ
- 作品領域は固定長とし、ランタイム本体と重ならないことをbuild時に確認する
- 空または不正な作品は実行せず、LEDとNeoPixelを安全な消灯状態にする
- 未知のopcode、範囲外の引数、途中で切れた命令は実行しない
- Blockly側で命令数、byte数、入れ子の深さ、待機時間に上限を設ける
- 最初のopcodeは内蔵LED、待機、繰り返し、終了に限定する
- 後から条件分岐、ボタン、NeoPixel、変数を追加できるversion付き形式にする
- `blockId`などブラウザ表示専用情報はボードへ保存しない

各bankを1024バイトとし、先頭16バイトをbank管理情報、続く1008バイトを作品領域とする。作品headerは16バイトで、payloadは最大992バイト。Flash/RAM実測後に、この領域を維持できるか再確認する。

bank管理情報は先頭から`UIAB`（4バイト）、version（1）、generation（4、little endian）、予約（1、0）、commit marker（2、`0x0000`）、予約（4、`0xFF`）とする。新しいbankの全データとCRCを確認した後、commit markerのhalfwordを最後に書く。起動時は有効な両bankのgenerationを比較して新しい方を選ぶ。

headerは次の形式とする。複数byteの数値はlittle endianで格納する。

| offset | 長さ | 内容 |
| ---: | ---: | --- |
| 0 | 4 | magic `UIBP` |
| 4 | 1 | 形式version。初期値は`1` |
| 5 | 1 | flags。bit 0は起動時の自動実行 |
| 6 | 2 | payload長 |
| 8 | 2 | payloadのCRC-16/CCITT-FALSE |
| 10 | 6 | 予約。version 1ではすべて`0` |

最初のopcodeは次のとおりとする。

| opcode | 命令 | 引数 |
| ---: | --- | --- |
| `0x00` | 終了 | なし |
| `0x01` | 内蔵LED | 状態1バイト。`0`消灯、`1`点灯 |
| `0x02` | 待機 | ミリ秒2バイト。`0`〜`5000` |
| `0x10` | 回数指定の繰り返し | 回数1バイト、body長2バイト、body |
| `0x11` | ずっと | body長2バイト、body |

繰り返し回数は1〜20、構造の入れ子は8段までとする。version 1のencoderはタクトスイッチ、NeoPixel、変数、論理演算を拒否し、未対応命令を別のopcodeへ読み替えない。

## 6. 起動と停止

- 有効な作品があれば、起動後に自動実行する
- 有効な作品がなければ、現在と同じWebHID教育用ランタイムとして待機する
- 単独実行中もWebHIDを受信できる非blocking実行器にし、待機や「ずっと」でUSB処理を止めない
- 電源断は任意の命令位置で起こるものとして扱い、再起動時は作品の先頭から始める
- 実行エラー時は出力を消灯し、作品の実行を停止する

作品の更新開始時は現在の作品実行を安全に停止し、出力を消灯する。更新成功後は新しい作品を先頭から開始する。通常のWebHID命令と作品実行が同じ出力を同時に変更しないよう、実行状態をランタイム側で管理する。

## 7. 通常接続での更新protocol

既存protocolの先頭8バイトを共通envelopeとして保ち、作品更新要求だけFeature Report全体の32バイトを使う。byte 7を追加payload長、byte 8〜31を追加payloadとし、すべての要求にsequenceと8バイト応答を持たせる。

- `PROGRAM_BEGIN`: 作品長、CRC、形式versionを通知する。範囲検査後、未使用bankだけを消去する
- `PROGRAM_DATA`: offsetと最大22バイトのデータを送る。連番・範囲・重複を検査して書く
- `PROGRAM_COMMIT`: 保存済みbyte列をFlash上で読み直し、長さ、CRC、bytecode構造を検証してから有効化する
- `PROGRAM_ABORT`: 未完了の更新を破棄し、直前の有効bankを維持する
- `PROGRAM_STATUS`: 有効bank、更新状態、受信済みbyte数、errorを返す

CH32V003 coreには1KiB単位の通常消去と64バイト単位の高速page消去がある。bank境界は両方に揃えている。消去・書き込み中にsoftware USBを長時間止めない単位を実機計測し、各操作の完了後に応答する。ブラウザは応答を待ってから次を送り、timeout時に自動で連続再試行しない。`PROGRAM_STATUS`の応答は`0x40`が対応済み・有効bankなし、`0x41`がbank A、`0x42`がbank Bを表す。

## 8. 書き込みの安全境界

### 通常導線

- 対象は通常動作モードのVID:PID `0x1209:0xD004`だけに限定する
- 書き込み先はFlash末尾2KiBの二重bankに固定し、ブラウザからアドレスを受け取らない
- linkerでランタイムを先頭14KiB以内に制限し、作品領域との重なりをbuild errorにする
- 使用中bankは消去せず、未使用bankを検証し終えるまで有効bankを切り替えない
- 長さ、CRC、形式、opcode構造のすべてが正しい場合だけcommitする
- 更新開始・失敗時はLEDとNeoPixelを安全な消灯状態にする
- 実機で消去する前に、生成mapとbinで予約範囲がランタイム本体と重ならないことを自動確認する

### 検証済み代替・復旧導線

- 対象はbootloaderのVID:PID `0x1209:0xB803`だけに限定する
- 書き込み前に、ベースとなる完成済みランタイムのSHA-256を照合する
- 作品を埋め込める場所は、ビルド時に用意した一意な予約領域だけに限定する
- 生成後のファームウェアサイズが16KiBを超える場合は書き込まない
- 書き込み後は既存処理と同様に64バイト単位でverifyする
- 作品書き込みはUIAPduino上の現在のプログラムを置き換えることを明示する
- 配布中の空ランタイムを書き直せば復旧できる状態を維持する

## 10. フィジビリティ確認の記録

- [x] LED点滅作品を安全なbytecodeへ変換できる
- [x] 作品入りbinで変更される範囲が予約領域だけである
- [x] 書き込みとverifyに既存bootloader経路を使える
- [x] USBを外して再給電してもLED点滅が始まる
- [ ] 不正な作品では出力を消灯して停止する
- [x] 空ランタイムへ戻す復旧手順を確認できる
- [x] Flash/RAM使用量と作品の最大byte数を記録する

2026-10-02に、内蔵LEDを500msごとに点灯・消灯する「ずっと」作品を1024バイトの予約領域へ埋め込み、公式`uiapflash`で書き込みと8320バイトのverifyに成功した。アプリ起動直後に点滅し、USBを外してボタンを押さずに再接続した後も、ブラウザから命令を送らず自動で点滅を再開することを実機確認した。

当時の空作品ランタイムはFlash 8096 / 16384バイト（49%）、RAM 232 / 2048バイト（11%）。作品payloadはheaderを除く最大1008バイトだった。現在の二重bank版はFlash 9596 / 14336バイト（67%）、RAM 248 / 2048バイト（12%）、作品payload最大992バイト。通常接続での更新は実機未確認。

同日、作品入りランタイムから空作品ランタイムへ書き戻し、8320バイトのverify、通常動作モード`0x1209:0xD004`への復帰、LED点滅の停止を確認した。
