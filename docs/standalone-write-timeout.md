# 作品保存の応答timeout（#65）

## 結論と変更の分離

失敗箇所は通常接続での作品保存通信（BEGIN／DATAの完了応答待ち）。確定した復帰処理の不備は、2026-10-02の機能導入コミット`8f26624`（`feat: prepare normal mode Blockly program updates`）から存在していた。これは不備の導入時点であり、実機で応答喪失が発生し始めた時点を示すものではない。USB／OSを含め、最初の応答喪失原因は未確定。

変更は次の2コミットへ分離する。

1. ブラウザの保存・復帰処理と回帰テスト。ファームへ診断命令を追加しなくても利用できる修正。
2. 読み取り専用のBEGIN診断機能、そのテスト、本調査記録。診断非対応のファームでも復帰処理を継続する。

配布bin・build-info・ZIPはこの調査では更新しない。診断版は実機確認用であり、ソースと配布物の差分を残している。以下は調査の時系列記録で、「これから」「未導入」等の記述はその時点の状態を表す。配布版ファームとの再確認と、成功時の通信ログ取得は未実施。

## 実機の証拠（2026-10-18）

- 保存開始10:01:17.872 UTC、失敗10:01:27.896 UTC。応答timeout 10,000ms。
- ユーザーは進捗%が一度も出なかったと報告した。
- その後、USBを抜かずに読み取り専用STATUSが成功し、保存先Aを返した。

この実装ではSTATUS／CAPABILITIESは2秒、BEGINとCOMMITだけが10秒待機する。進捗%はDATAの応答後なので、今回の事象はBEGINの応答待ちへ絞れる。後からSTATUSが返ったため、恒常的なUSB切断やボード全体の停止とは判断しない。Aが有効で新作品の保存完了を確認できていない。非アクティブ側が実際に消去されたか、BEGINをボードが受けたか、USB側で応答が失われたかは、元のログからは判定できない。

**最初の応答喪失の理由は未確定。** 以下の確定したソフトウェア上の不備を直しただけで、実機の最初のタイムアウト原因まで特定できたと扱わない。ファームのFlash消去前後のUSB動作等は候補だが、証拠がないため変更していない。

## 確認できた不備

1. BEGINが受理されACKだけ失われると、旧コードは`began=true`へ到達しない。そのためABORTを送らず終了し、ボードの更新状態が残り得る。再度BEGINを送っても更新中として拒否される可能性がある。
2. `withRuntimeResponseTimeout(transport.receive())`は外側の待機を終了するだけで、transport内の受信待ち行列から項目を削除しない。同じtransportでABORTを送って待つと、その応答を古い受信待機が消費し、復帰確認まで失敗し得る。
3. COMMITも「実行されたがACKが失われる」場合がある。単に再送やABORTをすると保存済み作品へ不要な影響を与える。

履歴を確認すると、通常接続保存導入の`8f26624`時点で1と2の構造が存在する。直近の色入力の変更`83f9a5e`は対応形式6の許可追加だけで、この後処理を変更していない。したがって「直近の色機能が保存処理を壊した」とは根拠なく結論しない。

## 変更

- BEGINを送る前から受理の可能性を記録し、応答不明時にはABORTで更新状態の解除を試みる。明示的なBEGIN拒否時は不要なABORTを送らない。
- 復帰前に古いtransportをdisposeして受信待機を終了し、新しいtransportで復帰応答を待つ。遅れたBEGIN応答等はcommandとsequenceで排除する。
- BEGIN・DATA・COMMITを自動再送しない。消去と書き込みを繰り返して成功扱いにしない。
- COMMIT応答不明時は新しい受信経路からSTATUSを読み、期待するbankへ切り替わった場合は成功として扱う（同時に別の書き込みを行わない前提）。STATUSでも確認できなければ、結果不明として再書き込みを避ける案内を出す。これは内容の読み戻し・世代番号確認そのものではない。
- SEND／SENT／RESPONSE／IGNORED／FAILED／RECOVERYを記録し、command、sequence、DATA offset、status、経過時間を残す。作品の本文は記録しない。エラー表示にも元の失敗段階を付ける。
- stale応答の度にtimeoutを最初から延長せず、1回の送信に対する待機期限内で処理する。

ABORTは既存ファームの契約に従い、保持している有効な作品を再選択する。旧作品が自動実行を再開する可能性があるため、全出力の停止が継続すると保証しない。ファーム、配布bin、bank配置は変更していない。

## 再発防止テスト

従来の模擬デバイスは通常、受けた命令へ即時応答していたため、ボードの処理成功とブラウザのACK受信成功を区別できていなかった。状態付きの応答喪失テストを追加する。

- BEGIN受理後のACK喪失：ABORT応答を受け、更新状態解除、次の保存が成功。
- ABORT中に遅れたBEGIN応答が到着：古い応答を無視し、正しいABORT応答を確認。
- DATA応答喪失：ABORTで終了し、BEGIN／COMMITの自動再送なし。
- ABORT応答も喪失：解除未確認を明示し、最初の失敗段階を保持。
- COMMITのACKだけ喪失：STATUSで切替先を確認し、COMMIT再送／ABORTなし。
- COMMITと確認STATUSも喪失：結果不明とし、破壊的な再送なし。
- すべての終了経路で受信リスナーを解除。既存の非対応形式の消去前拒否も維持。

追加した最初の4ケースは旧実装へ戻した比較実行で失敗し、修正版では成功した。改良後は全279件成功。これらはブラウザ側の復帰契約のテストで、実USBやFlashの応答喪失原因を実機で再現するものではない。

## 実機で次に確認すること

未修正コードで残った更新状態を持ち越さないよう、元の診断ログを保存した後にUSBを通常接続で挿し直す。ページを再読み込みして接続し直し、保存操作を1回だけ行う。新しい通信ログを採取し、BEGINの送信完了、応答有無、復帰の成否を確認する。自動的な消去リトライやファームの再導入は行わない。正常保存・再給電も実機で再確認してから完了を判断する。

## 追加ログによる実機確認（2026-10-18）

10:21 UTCの再確認でSTATUSは22ms（0x41、bank A）、CAPABILITIESは6ms（0x56、形式6）で正常応答。BEGINの送信APIは8msで完了し、10,011ms経っても対応する応答がなかった。その後ABORTは15msでstatus=0を返し、更新状態解除の応答を実機確認した。受信待機の破棄を含む復帰処理は動いたが、最初の保存失敗は再現しているため解決済みとはしない。

送信API完了は、ボードのアプリ処理完了やACKをブラウザが受けたことを意味しない。BEGINとABORTはどちらも出力停止を通るが、BEGINだけがFlashの消去・全域検査を伴う。FlashとUSBの関係は有力な調査箇所だが、これだけで原因とは断定しない。

## 診断用ファームの準備

読み取り専用command0x26を追加した候補をビルド。共通封筒の応答payloadへ、直前BEGINの処理段階・結果・更新中か・応答をキューへ入れたか・送信待機中かを格納する。

| ビット | 内容 |
| --- | --- |
| 7 | programUpdateActive |
| 6〜4 | 段階: 1=入口、2=出力停止後、3=消去直前、4=消去から復帰、5=消去結果検査後、6=更新状態設定済み |
| 3 | BEGIN応答をWebHID.sendへ渡した |
| 2 | 診断応答を送る直前のUSB TX busy |
| 1〜0 | BEGINの結果status |

例えば0xe8は更新中・段階6・応答キュー済み・TX busyなし・status0。これはボードの開始処理が完了し応答をUSBへ渡したことを示すが、USBホストのACKやブラウザへの配信まで保証するものではない。キューが空でも実際の配信失敗はあり得る。

ブラウザはBEGINの応答不明時だけ、ABORTの前にこの診断を読む。旧ファームのunsupported（1）や診断timeoutは記録し、復帰処理は継続する。BEGIN／Flash消去を再送する命令ではない。診断関数を実ソースから抽出してC++として検査し、ビットの組み合わせと状態を変更しないことを確認した。全280件成功。

候補binは12,528 / 14,336 bytes（空き1,808）、静的RAM444 bytes。基準12,416／440からFlash112 bytes・RAM4 bytes増。SHA-256はf925c8fd682eb5ce96daa06fd6c53baa86604e65a3f950a4536341526b538ffc。まだ実機へ導入しておらず、配布bin・メタデータ・ZIPは安定版のまま。この段階のソースと配布物は未同期。診断コード追加自体がタイミングを変え得るため、新ファームで症状が消えただけで原因確定とはしない。

次は利用者に書き込みモード接続を依頼し、診断用候補を導入して保存1回分のログを採る。原因判明後に必要な修正と回帰テストを判断する。診断機能は現時点で障害そのものの修正ではない。

利用者の書き込みモード接続後、上記ハッシュの診断用候補を公式uiapflashで導入した。12,544 bytesへパディングされ、全領域の読み戻し照合・アプリ起動が成功した。通常接続でのBEGIN診断ログはこれから取得する。配布物は変更していない。

## 診断版導入後：DATAでの応答喪失（2026-10-18）

10:45 UTCのログではBEGINは77msでstatus0を返したが、DATA offset0／sequence3の送信API完了後、2,008ms経って応答timeoutとなった。ABORTは14msで成功した。BEGINだけに限定した検証エラーではなく、Flashを伴う命令後の応答経路を継続調査する。診断版でBEGINが通ったのはタイミング変化の可能性があり、修正完了とは扱わない。

インストール済みcore1.2.14のWebHID Only実装を確認すると、Input Reportはusb_send_dataを呼んだ直後にwebhid_tx_pendingを0にしている。これはアプリ側でホストのACKを確認して再送するキューではない。一方、usb_handle_hid_get_report_startは直前のwebhid_tx_bufを読み出し専用GET_REPORTへ返す。この2経路を利用すれば、書き込み命令を再送せずにボードに残ったACKを確認できる。

### GET_REPORTでの限定的な応答確認

ブラウザ側だけへ追加。BEGIN／DATA／COMMITの送信APIが成功し、Input Report受信がRESPONSE_TIMEOUTになった場合に限り、古い受信待機を破棄してGET_REPORT ID0を1回読む。8byte共通封筒と、0のReport ID付き9byteだけを受け付け、magic・version・command・sequenceをすべて照合する。別の応答や不正フレームを成功扱いしない。STATUSや対応形式照会の通常応答を先に受けた逐次処理で、1作品は最大46 DATA分割（sequenceの256周回以内）であることを前提にする。同じボードに別タブ等から同時送信しない。

一致するACKがあればFEATURE_RESPONSEとして記録して処理を続行する。成功のstatus以外は、元と同じエラー処理へ渡す。GET_REPORTが未対応・timeout・不一致なら、元の失敗段階を保持して診断・復帰へ進む。書き込み命令の自動再送はしない。通常経路でACKが届く場合にはGET_REPORTを使わない。

実機でFEATURE_RESPONSEが一致すれば、その要求をボードが処理してACKを作成したがInput Reportとしてアプリへ届かなかったことを切り分けられる。ただしGET_REPORTでの成功だけでは、USBバス上のどのタイミング・ACK・OS配信で失われたかまでは特定できない。物理層原因の確定には別途USBトレースが必要。

模擬デバイスに実際のACKキャッシュを持たせ、BEGIN・DATA・COMMITのInput応答だけを落としてもGET_REPORTで成功し、各書き込み命令は1回ずつであることをテストした。Report ID付き、sequence不一致の拒否、正常時にキャッシュを読まないことも追加。全283件成功、Webビルド成功。ファームの追加変更・再書き込みと配布物更新は行っていない。実機でのFEATURE_RESPONSE確認はこれから。応答喪失が頻発すると従来のtimeout分ずつ遅くなるため、まず信頼性と切り分けを確認し、速度改善は別途判断する。
