# UIAPduino Browser Studio

UIAPduinoをブラウザからプログラミング、実行、書き込みできる統合開発環境を目指すプロジェクトです。

最終的には、[UIFlow](https://uiflow.m5stack.com/)のように、ブロックを組み立ててハードウェアを制御し、初学者から経験者まで段階的に使える環境を目指します。Blocklyで作ったプログラムをWebHID経由でUIAPduinoへ送り、将来はブラウザからの永続保存やファームウェア書き込みにも対応する構想です。

## プロジェクトのゴール

このプロジェクトのゴールは、小学生向け教材だけを作ることではありません。

目指すのは、次の一連の体験をブラウザだけで完結できる、UIAPduino向けの開発環境です。

1. ブロックでプログラムを組み立てる
2. 接続したUIAPduinoですぐに試す
3. 入出力や実行状態を画面で確認する
4. プログラムを保存して、繰り返し改善する
5. 必要に応じてUIAPduinoへ書き込み、単独で動かす
6. 初学者向けブロックから、より高度な開発へ段階的に進む

小学生向けワークショップは、この開発環境の使いやすさ、接続の安定性、学習体験を確かめるための最初の実証実験として位置づけます。ワークショップ向けの要件を重視しつつも、それだけに最適化して将来の用途を狭めないようにします。

## 当面の実証実験

最初の実証実験では、小学生向けワークショップで次を検証します。

- 初めて触る人でもブラウザから接続できるか
- ブロックと実機の動きの関係を理解できるか
- 実行、停止、修正を短い間隔で繰り返せるか
- 接続失敗やUSB切断から自力または簡単な案内で復旧できるか
- 講師が多数の端末を無理なく支援できるか

ここで得られた知見を、一般向けのUIAPduino開発環境へ還元します。

## 初期アーキテクチャ

最初のバージョンでは、Blocklyで組み立てた処理をブラウザで管理し、WebHID経由でUIAPduinoを操作します。サイトはGitHub Pagesで公開し、ChromeまたはEdgeから利用します。

```text
Blockly
  ↓
ブラウザ内の実行エンジン
  ↓
WebHID
  ↓
UIAPduino
```

WebアプリのコードはBlockly機能とデバイス診断機能を `features/` 単位で分け、各機能の中を `components`、`hooks`、`utils`、`types` に整理しています。テストは実装ファイルと混在させず、`web/src/__tests__/` に機能別でまとめます。

公開先はGitHub Pagesに統一しています。Sites用の未使用設定だった `web/.openai/hosting.json` は不要なため削除しました。

## 現在の状態

Phase 0を進行中です。`32V003 / 0x1209:0xB803`へのWebHID接続から、読み取り専用RISC-V stubによる識別値 `0x00310510`の取得まで実機で成功しました。flashの読み取り専用preflightでは、`CTLR=0x00008080`、`OBTKEYR=0x03FFFFDC`、ロック中、read protectionなしを確認しました。

診断画面の下部には、接続、読み取り、dry-run、安全確認の結果を時刻付きで確認できる診断ログを用意しています。ログはページを開いている間だけブラウザ内に保持され、コピーまたは消去できます。サーバーへの送信や永続保存は行いません。

flash unlockの限定実機確認では、6 packetの完了後に `CTLR=0x00000200`、read protectionなしを確認しました。flash先頭64バイトの読み取りにも成功し、基準値 `CRC32=0xBED6A734`を取得しました。退避内容を復旧用binファイルとしてPCへ保存し、読み取り結果との完全一致を確認できます。

復旧用ファイルの完全一致を実機で確認できたため、次段階のerase・復元処理を1つの中断不可分な手順として実装し、自動テストで順序と失敗時の復旧を固定しました。

2026-09-06の初回実機試験で先頭4バイトだけが`0xFF`となり、自動復旧にも失敗したため、erase操作を停止しました。その後、保存済みの復旧用binを直接選び、書き込み前のbuffer初期化を行って元の64バイトを書き戻しました。全64バイトの完全一致と `CRC32=0xBED6A734`を実機で確認し、破損前の状態へ復旧済みです。erase操作は原因確認が終わるまで停止を継続します。

erase経路のオフライン再監査では、参照実装の52バイトstub、引数位置、`0x00400040`、実行マジック、完了フラグ位置が現在の実装と一致することを自動テストで固定しました。続いて、実機へeraseを送らず `CTLR / STATR / OBTKEYR`を読み、BUSY、書き込み保護エラー、処理完了フラグを表示・記録する読み取り専用診断を追加しました。

2026-09-08の実機診断では `CTLR=0x00008080`、`STATR=0x00008000`、`OBTKEYR=0x03FFFFDC`を取得しました。BUSY、書き込み保護エラー、処理完了、status modeはいずれも検出されず、status側のLOCKだけが有効でした。これはロック中の安全な待機状態と整合します。

Phase 0の実機通信調査と並行してPhase 1を開始し、Blocklyによる画面内プログラミングを追加しました。「LEDをつける／けす」「待つ」「繰り返す」を組み合わせ、最初から用意された3回点滅プログラムを画面内LEDシミュレーターで実行・停止できます。実行中のブロックは順番にハイライトされます。ブロックは変更のたびにブラウザ内へ自動保存し、次回表示時に自動復元できます。「最初のブロックに戻す」操作も用意しています。

作品は専用の `.uiap.json`ファイルとしてPCへ保存し、別のブラウザやPCで読み込めます。作品ファイルはversion付きで検証し、現在のブロックを置き換える前に確認します。この段階では実機へ命令を送信しません。

Phase 2の準備として、Blocklyの実行エンジンを `BoardAdapter`方式へ切り替えました。画面のLED表示と命令順のハイライトを分離し、将来は同じ中間命令列へ実機Adapterを接続できます。

UIAPduino HID Arduino core `1.2.14`のWebHID APIに合わせ、教育用ランタイムのLED命令と応答を8バイト形式で実装しました。ブラウザからのFeature Reportは最大32バイト、ボードからのInput Reportは8バイトで、内蔵LEDはArduino pin 2です。最小ランタイムはFlash 4004 bytes、RAM 172 bytesでコンパイルできました。まだ実機への書き込みとブラウザの実機Adapterは有効にしていません。

接続後のHID descriptorから実行モードを確認する読み取り専用表示も追加しました。現在確認済みの `32V003`はInput/Output Reportがなく、Report ID `0xAA`のFeature Reportだけを持つため、書き込み用bootloaderモードと判定します。教育用ランタイムを動かすには、別途ランタイム対応ファームウェアとReport仕様の確定が必要です。

書き込み前確認は危険操作の警告ではなく確認専用の画面として、情報色（青系）で表示する。実際に消去・書き込みを有効化する段階だけ、明確な警告色と最終確認を使う。
